# BrandCast 구현 계획서

작성일: 2026-11-27  
기준 DBMS: MariaDB  
분석 방식: MariaDB SQL  
Python 사용 범위: RACOI 자료 수집, MariaDB 연결, SQL 결과 표시, 그래프 작성 및 저장

## 1. 구현 목표

최근 1년의 RACOI 인터넷반응DB, 종합반응DB와 프로그램별 댓글반응 분석 데이터를 이용해 20~30대 여성 대상 신규 스킨케어 제품의 방송 PPL 후보를 검토한다.

모든 데이터 전처리, 집계, 지표 계산, 후보 선별과 순위 계산은 MariaDB SQL로 수행한다. Python은 공개 데이터 수집과 SQL 결과 시각화에만 사용한다. Q1~Q6 질문 노트북은 각각 계획된 그래프 2개와 충분한 중간 결과 테이블을 보여주고, 마지막에 해당 질문에 대한 결론을 작성한다.

## 2. 기준 문서와 규칙

구현을 시작하기 전에 다음 문서를 순서대로 확인한다.

1. `AGENTS.md`: 파일명, SQL 주석, GitHub, 데이터와 그래프 작업 규칙
2. `../문서/개발 계획서.md`: 비즈니스 문제, 6개 질문, 지표와 그래프 요구사항
3. `문서/노트북_프로젝트_구조_및_개발계획.md`: 현재 확정된 폴더와 노트북 구성
4. `docs/구현_계획서.md`: 실제 파일 생성 및 구현 순서

문서 간 내용이 다르면 사용자의 최신 요청과 `AGENTS.md`를 우선한다.

## 5. 단계별 구현 계획

### 단계 1. 실행 환경 준비

#### 생성 파일

- `requirements.txt`
- `.env.example`
- `.gitignore`

#### 구현 내용

`requirements.txt`에는 Jupyter, JupySQL, SQLAlchemy, MariaDB 연결 드라이버, 수집 라이브러리와 시각화 라이브러리를 기록한다. 실제 패키지는 구현 시 선택한 수집 방식에 필요한 것만 추가한다.

`.env.example`에는 값 없이 다음 설정 이름을 기록한다.

```text
MARIADB_HOST=
MARIADB_PORT=
MARIADB_DATABASE=
MARIADB_USER=
MARIADB_PASSWORD=
RACOI_BASE_URL=
DATA_START_DATE=
DATA_END_DATE=
```

#### 완료 기준

- 실제 비밀번호가 저장소 파일에 없음
- 원본 데이터와 원문 댓글이 Git 추적 대상에서 제외됨
- MariaDB 연결에 필요한 설정 이름이 문서화됨

### 단계 2. 프로젝트 소개와 분석 페르소나 작성

#### 생성 파일

- `프로젝트_소개/00_프로젝트_소개와_분석_페르소나.ipynb`

#### 필수 내용

- 프로젝트 대제목
- 핵심 질문: 이 프로젝트는 누구의 어떤 의사결정을 지원하며 무엇을 해결하는가?
- 프로젝트 배경과 RACOI 선택 이유
- 뷰티 브랜드 마케팅팀/미디어 플래너 페르소나
- 신규 스킨케어 제품과 20~30대 여성 타깃
- 방송 PPL과 SNS 연계 캠페인 의사결정
- Q1~Q6의 역할과 후보 축소 흐름

- 프로젝트 소개표와 페르소나 요약표

#### 완료 기준

- 프로젝트 소개와 페르소나가 한 노트북에서 자연스럽게 연결됨
- 실제 광고 효과나 ROI를 입증한다고 표현하지 않음
- Q1~Q6이 왜 필요한지 설명됨

### 단계 3. RACOI 수집 코드 구현

#### 생성 파일

- `수집/RACOI_자료_내려받기.py`
- `수집/수집_실행.py`

#### 수집 대상

1. 인터넷반응DB 최근 1년 주간 데이터
2. 종합반응DB 최근 1년 월간 데이터
3. `pjseq=11487`을 시작으로 확인한 댓글반응 분석 자료

#### 구현 원칙

- 공식 다운로드가 있으면 HTML 표 파싱보다 다운로드를 우선한다.
- 원본 응답은 수정하지 않고 `데이터/원본`에 저장한다.
- 요청 URL, 수집 시각, 대상 기간, 파일명, 체크섬, 성공 여부를 기록한다.
- 같은 기간과 파일을 다시 실행해도 중복 저장을 통제한다.
- 댓글 원문 전체 수집보다 RACOI가 공개하는 키워드·감성·연관어 결과를 우선한다.

#### 완료 기준

- 세 데이터 원천의 소량 시범 수집 성공
- 파일명에 원천과 기간이 표시됨
- 실패가 성공으로 기록되지 않음
- 지정 프로그램 댓글반응 페이지의 실제 제공 항목이 확인됨

### 단계 5. MariaDB 적재·품질·전처리 노트북 작성

#### 생성 파일

- `노트북/02_데이터_적재_품질_및_전처리.ipynb`

#### 구현 순서

1. MariaDB 연결과 버전 확인
2. 원본 테이블 생성
3. 원본 파일 적재
4. 원본 데이터 표본 표시
5. 중복·결측·숫자·날짜·기간 품질검사
6. 분석용 테이블 생성
7. 분석용 테이블 표본 표시
8. 원본과 분석용 테이블 행 수·합계 비교
9. 분석 기간 커버리지 확인
10. 전처리 결과와 남은 문제 결론

#### 원본 테이블 초안

| 테이블 | 역할 |
|---|---|
| `raw_internet_response` | 인터넷반응 원본 |
| `raw_total_response` | 종합반응 원본 |
| `raw_comment_analysis` | 댓글반응 분석 원본 |
| `raw_ingestion_log` | 수집 실행과 원천·기간 이력 |

#### 분석용 테이블 초안

| 테이블 | 한 행의 단위 |
|---|---|
| `analysis_program` | 프로그램 1개 |
| `analysis_program_weekly` | 프로그램·주차 1행 |
| `analysis_program_monthly` | 프로그램·월 1행 |
| `analysis_audience_weekly` | 프로그램·주차·연령·성별 1행 |
| `analysis_keyword_weekly` | 프로그램·주차·키워드 1행 |
| `analysis_sentiment_weekly` | 프로그램·주차 1행 |

실제 원본 컬럼을 확인한 뒤 테이블 수와 컬럼을 확정한다. 제공되지 않는 데이터를 가정해 빈 컬럼을 만들지 않는다.

#### 완료 기준

- 모든 SQL 셀에 한국어 주석이 있음
- 원본 테이블이 전처리 과정에서 수정되지 않음
- 미수집과 실제 0이 구분됨
- 분석용 테이블의 한 행 단위와 키가 확인됨
- 중요한 변환 단계마다 결과 표가 표시됨

## 6. Notebook 공통 작성 원칙

Q1~Q6의 셀 순서는 고정하지 않는다. 분석 흐름에 따라 자유롭게 구성하되 다음 요소는 반드시 포함한다.

- 한국어 대제목
- 명확한 핵심 질문
- 결과가 도출되는 과정을 설명하는 한국어 Markdown
- 한국어 주석이 포함된 MariaDB SQL
- SQL 결과 테이블 1개 이상
- 중요한 데이터 변화 단계마다 추가 결과 표
- 계획된 그래프 2개
- 그래프의 노트북 표시와 질문별 폴더 저장
- 핵심 질문에 대한 명확한 결론

표는 가능한 한 자주 보여준다. 원본 확인, 품질검사, 전처리, 지표 계산, 후보 선별과 그래프 입력 데이터처럼 값이나 단위가 달라지는 지점에서 결과 표를 표시한다. 전체 행을 모두 출력하지 않고 보통 5~20행과 전체 행 수를 함께 보여준다.

## 7. SQL 작성 원칙

모든 SQL 셀의 상단에는 다음 주석을 작성한다.

```sql
-- 목적: 이 SQL이 해결하는 문제
-- 입력: 사용하는 테이블
-- 출력 단위: 결과 한 행의 의미
-- 분석 기간: 사용하는 기간과 기준일
-- NULL/0 처리: 미수집, 결측, 실제 0 처리 기준
```

CTE, JOIN, 윈도 함수, 회귀·백분위·표준화 계산, 후보 통과 조건과 동률 처리에도 처리 이유를 한국어로 설명한다. SQL 문법을 그대로 읽는 주석보다 해당 처리가 필요한 이유를 작성한다.
