# RACOI 뷰티 브랜드 미디어 선정 프로젝트 개발 계획

> 프로젝트 기획의 기준 문서는 저장소 상위 폴더의 `../문서/개발 계획서.md`다. 이 문서는 그 계획을 Jupyter Notebook 중심의 폴더·파일 구성과 데이터 수집 순서로 구체화한다. 이 문서 안의 초안은 실제 수집 결과나 RACOI 내부 데이터 스키마를 보증하지 않는다.

## 1. 프로젝트 대제목과 최종 핵심 질문

### 대제목

**20~30대 여성 대상 스킨케어 브랜드의 방송 PPL 후보 선정**

### 최종 핵심 질문

**최근 1년 동안의 RACOI 시청층·인터넷 반응·종합 반응·댓글 분석 근거를 결합했을 때, 핵심 고객과 접점이 있고 뷰티 메시지와 어울리며 관심이 지속되고 브랜드 감성 위험을 관리할 수 있는 방송 프로그램은 무엇인가?**

광고비, 노출 결과, 구매 전환 자료가 없으므로 결론은 상대적인 광고 후보와 검토 근거다. 광고 효과나 ROI를 예측·입증한다고 말하지 않는다.

## 2. 기획서 요구와 실행 규칙 구분

`../문서/개발 계획서.md`는 비즈니스 시나리오, 여섯 질문, 후보 퍼널, 지표와 산출물의 **프로젝트 요구사항**으로 반영한다. 문서 속 구현 지시 문구를 저장소 운영 규칙으로 자동 간주하지 않는다. 실제 작업 규칙은 저장소 루트의 `AGENTS.md`와 사용자의 최신 요청을 따른다.

기존 계획서의 계산 원칙은 유지한다. 수집은 Python, 데이터 전처리와 분석 지표 계산은 SQL, 시각화는 Python으로 책임을 나눈다. 즉 Python 크롤링은 허용된 수집 작업이며 Python에서 분석용 정제·집계·통계·후보 순위를 계산하지 않는다.

### SQL과 노트북의 배치 원칙

SQL을 별도 파일로 분리하면 재사용하기 쉽지만, 이 프로젝트는 노트북에서 전체 과정을 설명하고 결과를 보여주는 것이 목적이다. 별도 SQL 파일을 두면 독자가 노트북과 SQL 파일을 계속 오가야 하므로 `SQL/` 폴더를 만들지 않는다.

모든 SQL은 실행 목적에 맞는 노트북 안에 둔다.

- `노트북/02`: MariaDB 테이블 생성, 원본 적재, 품질 진단, 전처리와 전처리 검증 SQL
- `노트북/03~08`: JupySQL의 `%%sql` 셀을 사용해 각 질문의 지표 계산, 후보 선별, 그래프 조회용 SQL을 직접 작성
- Python: SQL 연결·실행, 결과 표 표시, 계획된 그래프 2개 작성만 담당

이 구조라면 `02` 노트북에서 원본이 분석용 테이블로 바뀌는 과정을 모두 확인할 수 있고, 질문 노트북 한 개만 열어도 핵심 질문, SQL 계산, 중간 테이블, 그래프 2개와 결론을 순서대로 확인할 수 있다. 반복되는 SQL이 생기면 MariaDB 뷰로 만들되 뷰 생성 SQL도 해당 노트북에 남긴다.

Jupyter Notebook에서는 SQL 확장 기능을 이용해 `%sql` 또는 `%%sql` 셀을 실행할 수 있다. 이 프로젝트의 기준 DBMS는 **MariaDB**로 확정하며 JupySQL과 MariaDB 호환 드라이버로 연결한다. 연결정보는 환경변수에서 읽고 노트북에는 비밀번호나 전체 연결 문자열을 남기지 않는다. JupySQL은 SQL 실행과 결과 표시에 사용하며 분석 로직 자체는 MariaDB SQL 문장 안에 둔다.

### 단순한 데이터 구조

이 프로젝트는 운영용 데이터 플랫폼이 아니므로 RAW, STG, MART를 모두 나누지 않는다. 다음 두 단계만 사용한다.

1. **원본 테이블**: RACOI에서 받은 값을 가능한 그대로 적재하며 수정하지 않는다.
2. **분석용 테이블**: 원본에서 중복, 날짜·숫자 형식, 결측 상태, 프로그램 식별자를 정리해 질문 노트북이 바로 사용할 수 있게 만든다.

분석용 테이블을 하나로 합치지는 않는다. 주간 프로그램 반응, 월간 종합반응, 연령·성별 시청층, 키워드, 감성 데이터는 각 행이 의미하는 단위가 다르다. 이를 한 테이블로 조인하면 프로그램의 댓글 수나 조회 수가 연령·키워드 개수만큼 중복될 수 있다. 따라서 다음 최소 테이블만 둔다.

| 구분 | 테이블 | 한 행의 단위 |
|---|---|---|
| 원본 | `raw_internet_response` | RACOI 인터넷반응 원본 한 행 |
| 원본 | `raw_total_response` | RACOI 종합반응 원본 한 행 |
| 원본 | `raw_comment_analysis` | 댓글반응 분석 원본 한 행 |
| 원본 | `raw_ingestion_log` | 수집 실행·원천·기간 1건 |
| 분석 | `analysis_program` | 프로그램 1개 |
| 분석 | `analysis_program_weekly` | 프로그램·주차 1행 |
| 분석 | `analysis_program_monthly` | 프로그램·월 1행 |
| 분석 | `analysis_audience_weekly` | 프로그램·주차·연령·성별 1행 |
| 분석 | `analysis_keyword_weekly` | 프로그램·주차·키워드 1행 |
| 분석 | `analysis_sentiment_weekly` | 프로그램·주차 1행 |
| 분석 | `analysis_keyword_dictionary` | 정규화 키워드·주제·사전 버전 1행 |

Q1~Q6의 지표와 후보 순위는 노트북의 SQL CTE에서 계산한다. 여러 질문에서 반복해서 사용할 필요가 생긴 결과만 나중에 분석용 테이블이나 뷰로 추가한다.

### SQL 주석 필수 규칙

모든 노트북 `%%sql` 셀에는 한국어 주석을 작성한다. SQL 블록 상단에는 다음 정보를 적는다.

```sql
-- 목적: 20~30대 여성 타깃 비중과 시장 대비 Lift 산출
-- 입력: analysis_audience_weekly, analysis_program_weekly
-- 출력 단위: 프로그램(pjseq) 1행
-- 분석 기간: :reference_week 기준 최근 완료 4주
-- NULL/0 처리: 미수집은 NULL 유지, 실제 관측 0과 구분, 0 분모는 NULL 처리

WITH target_audience AS (
    -- 타깃 연령과 성별이 일치하는 관측치만 프로그램·주차 단위로 집계한다.
    -- 연령 구간 중복으로 타깃 비중이 이중 계산되지 않도록 사전 품질 검사를 통과한 행만 사용한다.
    SELECT
        pjseq,
        week_start_date,
        SUM(audience_ratio) AS target_ratio
    FROM analysis_audience_weekly
    WHERE gender = '여성'
      AND age_group IN ('20대', '30대')
    GROUP BY pjseq, week_start_date
)
SELECT *
FROM target_audience;
```

주석이 필요한 위치는 다음과 같다.

- 각 SQL 셀 또는 파일의 전체 목적과 입출력
- CTE별 역할과 앞 단계와의 관계
- JOIN 키와 조인으로 행이 늘어날 가능성
- NULL, 실제 0, 미수집 값의 구분
- 백분위, 회귀, 표준화, 이동평균 등 계산식 선택 이유
- 후보 통과·탈락 조건과 동률 처리 기준
- 데이터 품질 문제로 지표를 비활성화하는 조건

`-- 프로그램별로 집계`처럼 코드만 다시 읽어주는 주석보다 `-- 서로 다른 주차의 중복 결합을 막기 위해 조인 전에 프로그램·주차 단위로 집계`처럼 처리 이유를 적는다.

## 3. 데이터 수집 범위 판단

### 필수 수집: 1년치 RACOI 정량 데이터

기준일을 정한 뒤 **가장 최근 완료된 1년**을 사용한다. 초기에는 인터넷반응DB에서 주간 프로그램 반응과 이용 가능한 타깃/연령별 자료를, 종합반응DB에서 월간 반응을 받는다. 1년 범위는 달력연도와 최근 12개월 중 어느 쪽인지 실행 설정에 명시한다. 권장 기본값은 최신 완료일 기준 최근 12개월이며, 공개 데이터의 보유 기간과 다운로드 단위를 확인해 확정한다.

두 DB 모두 가져오는 것이 타당하다. 주간 자료는 Q1, Q3, Q5와 주간 키워드·감성 흐름을, 월간 자료는 월 기준 온라인 반응과 시청규모 대비 관심 비교(Q2)를 맡긴다. 같은 지표라도 주간/월간 수치를 단순 합산하지 않는다. 인터넷반응DB와 종합반응DB의 정의가 중복되는지 확인하고 월간 값은 해당 DB의 공식 월간 값으로 취급한다.

RACOI 안내에 따르면 인터넷반응은 주간, 종합반응은 월간 단위이며, 미디어버즈(뉴스·동영상 수)와 시청자버즈(게시글·댓글·동영상 조회 수)를 제공한다. RACOI는 자료실에 Excel 데이터 다운로드 경로도 노출한다. 따라서 HTML 크롤링만을 유일한 수집법으로 가정하지 않고, 다운로드 버튼/API 또는 공개 응답 중 재현성 있는 원본 경로를 실제 확인한 뒤 수집 방식을 확정한다. (공식 안내: https://kobaco.co.kr/site/main/content/racoi_info, https://www.racoi.or.kr/kobaco/excel/response.do?menu=ibuzz)

### 댓글 상세 분석: 포함하되 단계적 수집

사용자가 지정한 `https://www.racoi.or.kr/kobaco/nreport/pjinfo.do?pjseq=11487` 프로그램 상세 페이지의 댓글반응 분석을 Python 수집 대상으로 둔다. 우선 페이지에 공개된 주차별 댓글 키워드, 긍·부정/감성, 연관어·공출현 결과 및 다운로드 항목을 확인한다. 이 상세 자료는 Q4의 뷰티·자기관리 주제 적합성을 해석하고 Q6의 부정 반응 맥락을 검토하는 보강 자료로 쓴다.

1년치 모든 프로그램의 개별 원문 댓글을 무차별 수집하는 것은 1차 범위로 삼지 않는다. 우선 1년치 전체 프로그램에 대해 RACOI의 공식 집계치·키워드·감성 필드를 수집하고, 댓글 상세 페이지의 공개된 구조화 결과는 분석 후보의 검증에 쓴다. 원문 댓글 수집이 실제로 필요하고 공개 페이지/다운로드 경로에서 접근 가능하면, 초기 표본(지정 프로그램 11487)으로 데이터 형태·중복·기간·수집량을 확인한 뒤 최종 후보 또는 지정 프로그램만으로 범위를 넓힌다. 원문 내용의 보관은 분석에 필요한 최소 범위로 제한하고 저장소에는 넣지 않는다.

RACOI는 웹사이트에서 HTML/Excel 응답을 제공한다. 이는 공개 페이지의 구조화된 자료를 크롤링할 수 있다는 전제로 설계할 근거다. 단, 상세 페이지의 실제 반환 항목과 요청 제한은 구현 시 확인한다. 세션·접근제어 우회나 비공개 경로 호출은 하지 않고, 공개 화면에서 내려받을 수 있는 자료를 수집한다. 원문 댓글이 페이지에 표시되지 않고 요약 분석만 제공된다면 해당 요약만 수집하고 원문을 임의 복원하지 않는다.

### 가져오지 않을 데이터(초기 범위)

- 해외 반응 및 OTT 반응: 현재 질문은 국내 방송 PPL 후보 비교이므로 별도 확장 범위로 둔다.
- SNS 원문 전체: Instagram/X를 포함한다고 가정하지 않는다. RACOI 조사 대상과 실제 제공 범위를 먼저 확인한다.
- 광고비·슬롯·실제 PPL 가능 여부: RACOI에서 얻는 자료가 아니므로 최종 후보 선정 뒤 별도 확인 항목으로 표시한다.

## 5. Notebook 공통 구성

Q1~Q6 질문 노트북의 셀 순서와 중간 구성은 고정하지 않는다. 분석 내용에 맞게 자연스럽게 구성하되 다음 요소는 반드시 포함한다.

- 한국어 대제목
- 해당 노트북이 답할 핵심 질문
- 데이터가 어떻게 가공되고 결론으로 이어지는지 설명하는 한국어 Markdown
- 주석이 포함된 MariaDB SQL 셀
- SQL 결과 테이블 1개 이상
- 개발 계획서에서 해당 질문에 지정한 그래프 2개
- 그래프 2개의 노트북 표시와 해당 질문 그래프 폴더 저장
- 핵심 질문에 대한 명확한 결론

테이블은 최소 개수만 맞추는 방식으로 만들지 않는다. 원본 형태 확인, 결측·중복 확인, 지표 계산, 후보 선별처럼 데이터가 달라지는 중요한 지점마다 SQL 결과를 바로 표로 보여주는 것을 권장한다. 노트북이 지나치게 길어지지 않도록 보통 5~20행을 표시하고 전체 행 수를 함께 적는다.

`02_데이터_적재_품질_및_전처리`는 다음 네 작업을 순서대로 실행하고 설명한다.

1. `CREATE TABLE`로 원본·분석용 테이블 생성
2. 수집 파일을 원본 테이블에 적재
3. 원본 데이터 품질 확인 후 분석용 테이블 생성
4. 원본/분석 테이블 행 수, 중복, 결측, 기간과 집계값 비교

Python으로 CSV를 수정하거나 pandas의 `groupby`, 통계 함수 등으로 분석 데이터를 만들지 않는다. Python은 MariaDB 연결과 파일 경로 전달에만 사용하고 적재·전처리·검증은 주석이 포함된 MariaDB SQL 셀에서 처리한다.

질문 노트북에서 표를 보여주기 위해 SQL 결과를 DataFrame으로 받아도 된다. DataFrame은 화면 표시와 그래프 입력 전달에만 사용한다. 정렬, 필터, 집계, 비율, 백분위, 회귀, 순위 및 후보 판정은 SQL 결과에 이미 포함되어 있어야 한다.

### 질문 노트북에서 보여주기 좋은 테이블

| 분석 지점 | 표시할 내용 | 권장 표시량 |
|---|---|---:|
| 입력 확인 | 사용할 컬럼, 프로그램명, 기간, 원천 값 | 5~10행 |
| 품질 확인 | 전체 행 수, 프로그램 수, 기간 수, 중복, NULL, 제외 건수 | 항목별 요약 1표 |
| 지표 계산 | 질문별 핵심 파생 지표와 단위 | 상위 10~20행 |
| 후보 선별 | 이전 단계 순위, 현재 순위, 통과 여부, 제외 사유 | 후보 전체 또는 상위 20행 |
| 그래프 입력 | 그래프가 실제 사용하는 SQL 결과 | 그래프별 5~10행 |

표 전체를 무제한 출력하지 않는다. 노트북에는 일부 행과 전체 행 수를 함께 보여주고, 전체 결과는 DB의 결과 뷰 또는 `데이터/결과/`의 비식별 집계 파일로 관리한다.

## 7. 전처리 및 기간 기준

- 수집 이력, 원본 체크섬, 요청 URL, 수집 시각, 파일 형식, 대상 기간과 행 수를 기록한다. 재실행 시 같은 응답을 중복 적재하지 않도록 한다.
- 기준 DBMS는 MariaDB다. `SELECT VERSION()`으로 사용 버전을 기록하고 해당 버전에서 지원하는 윈도 함수와 SQL 문법을 사용한다.
- 프로그램 식별자는 `pjseq` 우선으로 연결한다. 프로그램명·채널은 보조 매칭에만 사용하고 모호한 매칭은 자동 병합하지 않는다.
- 테이블별 grain을 문서화한다. 예: 프로그램-주차, 프로그램-월, 프로그램-주차-연령-성별. 조인 전에 같은 grain으로 집계하고 조인 전후 행 수를 비교한다.
- 미수집/누락은 `NULL` 또는 품질 상태로 남기며 0과 구분한다. 중복·이상치·식별 실패는 원본 삭제 대신 SQL 정제 결과와 제외 사유로 추적한다.
- 시청자 수와 시청층 비율의 모집단이 일치하는지 검증한다. 불일치 시 타깃 비중/Lift만 쓰고 타깃 인원 규모를 산출하지 않는다.
- 1년치 전체 데이터는 월·주별 커버리지 표를 먼저 만든다. Q1/Q3/Q4는 최근 완료 주차 기준, Q2는 최근 완료 월 기준, Q5/Q6은 8주/최근 4주 기준이라는 계획을 적용하되 실제 커버리지에 따라 기간을 조정하고 기록한다.
- Q2에서 12개월을 전부 분석할지 최신 3개월 기본 설계를 쓸지 결과를 보고 임의 선택하지 않는다. 1년 시계열과 최신 3개월 판단을 분리해 출력하고, 1년 데이터는 계절성/강건성 확인에 사용한다.

## 8. 크롤링 구현 범위와 안전한 수집 구조

`수집/RACOI_자료_내려받기.py`는 페이지 탐색·다운로드·원본 보존만 한다. 페이지에서 공개된 내려받기 링크가 있으면 그 응답 파일을 저장하고, 상세 페이지에서 HTML 테이블/JSON 데이터가 공개되면 응답을 원본으로 저장한다. 브라우저 렌더링이 필요한지 확인한 다음 일반 HTTP 요청과 브라우저 자동화 중 간단하고 재현 가능한 수단을 선택한다. 파싱은 수집 포맷을 식별하고 SQL에 적재 가능한 원본 행으로 옮기는 데 한정한다.

수집 레코드 메타데이터: `source_name`, `source_url`, `collected_at`, `period_start`, `period_end`, `pjseq`(해당 시), `http_status`, `content_type`, `checksum`, `row_count`, `ingestion_status`. 실패한 다운로드는 성공으로 기록하지 않는다. 기간/프로그램/페이지 단위 요청을 직렬 또는 보수적인 속도로 보내고, 캐시·재시도 간격을 둔다. 쿠키·개인 계정 정보·사용자 식별자를 원격 저장소나 로그에 기록하지 않는다.

1차 수집 순서는 (1) 사이트 이용가이드/다운로드 범위 확인, (2) 지정 프로그램 `pjseq=11487`의 상세 페이지와 댓글 분석 제공 항목 확인, (3) 인터넷반응 주간 1년, (4) 종합반응 월간 1년, (5) 상세 결과의 커버리지와 결측 비교다. 지정 프로그램 상세 페이지가 최신 연도만 보여준다면 가능한 기간을 명시하고, 없는 과거 자료를 만들어내지 않는다.

## 9. 그래프 디자인 기준

- 시각화는 SQL이 반환한 분석 결과에서만 만든다. Python은 색상, 정렬된 레이블, 주석, 레이아웃을 적용하는 용도다.
- 기본 글꼴은 사용 가능한 한글 산세리프 폰트를 탐지해 명시한다. 폰트가 없으면 글자 깨짐을 경고하고 폰트 설정 안내를 표시한다.
- 색상은 의미를 일관되게 사용한다: 기준/전체 집단은 중립 회색, 후보는 파랑/청록, 긍정은 청록, 주의·위험은 호박/적색. 색상만으로 의미를 전달하지 않고 라벨과 범례를 함께 둔다.
- 차트마다 질문형 제목, 측정 단위, 기간, 모집단/표본수, 데이터 출처를 넣는다. 상위 막대 차트는 프로그램명이 잘리지 않게 가로형으로, 분포 차트는 관측치와 선택 후보를 구분한다.
- 단일 노트북 안에서 같은 질문의 그래프는 크기·색·숫자 포맷을 통일한다. 과도한 장식과 3D 차트는 피하고 발표 화면에서도 읽히도록 만든다.

6. 여섯 질문의 SQL을 각 질문 노트북에 작성하고, 중간 테이블과 계획된 그래프 2개씩을 제작한다.
7. 단계별 후보, 제외 이유, 데이터 충분성, 한계, 전체 후보와 퍼널 후보 간 차이를 재현 가능한 결과로 정리한다.

완료 시점에는 1년치 기간 커버리지, 자료별 행 수·중복·결측률, 주간/월간 단위 정의, 댓글 상세 제공 범위, SQL 품질 점검 결과, 그래프 12개, 후보 퍼널과 근거, 데이터 미확보 또는 불확실 항목을 모두 보고한다. 실제 데이터가 준비되기 전에는 후보명이나 수치를 예시로 꾸며 내지 않는다.

## 11. GitHub 규칙

커밋 메시지, 이슈 제목, PR 제목은 한국어로 작성하고 명사형으로 끝낸다. 제목은 작업 범위를 구체적으로 표현한다. 예: `RACOI 연간 데이터 수집 설계`, `댓글 분석 범위와 보안 규칙 정리`, `Q1 타깃 적합도 산출 SQL 추가`.

이슈와 PR은 배경, 목표, 상세 작업, 파일/데이터 영향, 재현·검증 방법, 결과, 한계와 후속 작업을 자세히 작성한다. 적절한 label을 붙이고 사용자를 담당자로 할당한다. 실제 저장소의 label 목록과 GitHub 사용자명을 확인한 뒤 적용한다. 커밋 메시지 끝에도 명사형 제목 규칙을 적용한다.

이슈·PR 생성이나 원격 push는 별도 요청이 있을 때 진행한다. 외부 게시 작업을 실행할 때에는 비밀정보·원문 댓글·원본 수집자료가 포함되지 않았는지 확인한다.
